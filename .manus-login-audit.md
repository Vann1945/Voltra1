# Login audit notes

## Reproduction

- Repository: `Vann1945/Voltra1`
- Branch: `main`
- Commit: `2092a5aed04f017a29e506b68babbb6965ba811e`
- Environment: local Next.js dev server at `http://localhost:3000`
- Browser viewport: approximately 895×768 screenshot viewport
- Steps: navigate to `/login?error=OAuthCallback`
- Expected: return to the marketplace, show a recoverable authentication error, and reopen the sign-in UI.
- Actual: page renders only the global navbar and an otherwise blank main area; URL remains `/login?error=OAuthCallback` after waiting.
- Evidence: screenshot `/home/ubuntu/screenshots/localhost_2026-08-27_06-37-45_1482.webp` and browser HTML `/home/ubuntu/browser_html/localhost_login_1787812667251.html`.

## Root-cause hypothesis

`app/login/LoginRedirect.tsx` uses `useEffect`, `useRouter`, and `useSearchParams` but does not declare `'use client';`. The fallback route therefore does not execute its client redirect in the browser. It also renders `null`, so the user receives no progress or recovery affordance while the redirect is pending.

## Baseline checks

- `npm ci --ignore-scripts`: passed.
- `npm run lint`: passed.
- `npm run build`: passed; Next.js 15.5.23 generated 26 static pages.
- No live OAuth/TiDB credentials were available locally, so provider callback completion remains blocked for this environment.

## Initial visual/UX findings

- Login is modal-only from the marketplace; the dedicated `/login` fallback has no meaningful UI.
- Auth modal closes on Escape/backdrop but does not implement focus trapping or initial focus management.
- The form has no password visibility toggle, submits with an opaque loading skeleton, and uses a separate reCAPTCHA widget on every modal mount.
- Error feedback is shown as text but the modal does not autofocus the first invalid field or expose a concise recovery path for provider failures.
- Auth provider buttons and form controls can be consolidated with stable states to reduce layout shift and repeated markup.

## Post-patch browser verification

The production server served `/login?error=OAuthCallback` as a complete login screen with actionable provider-error copy, a responsive two-column layout, provider controls, password visibility toggle, and visible CAPTCHA fallback text. The shared marketplace sign-in entry point mounted the redesigned modal successfully. The password toggle changed the input type from `password` to `text` and changed its accessible label from “Show password” to “Hide password”. Submitting empty credentials exposed inline email and password errors without a network request. The forgot-password transition removed the password/provider controls and restored them when returning to sign in; CAPTCHA remains mounted because the reset endpoint requires it.

## Production smoke-test outcome

The current production build served the dedicated login page successfully and rendered its provider-error, fields, password toggle, CAPTCHA fallback, and recovery UI. The dynamic `/addons/test` route also returned its intended “Add-on not found” state without the previous `DOMPurify.addHook is not a function` startup crash. Requests that require TiDB still log an expected environment limitation because `TIDB_HOST` is not available in the sandbox; live credentials were intentionally not supplied.
